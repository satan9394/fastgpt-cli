# Harness Requirements（需求分析）

在 harness 治理的项目里，新功能/大改动先过本 skill：**需求先立规格、验收先可判定**，实现才不跑偏。
本 skill 只负责「需求→规格→验收」这一段；评审判据与完成判定的口径委托核心 harness（见「委托」），不复制核心共享规则。

## When to Apply / Skip

**用**（两类触发）：

- **写规格**（需同时满足）：新功能/模块级改动且需求未定、边界不清；需求方只说「要个 XX」且没给可判定验收标准；改动跨多文件/多模块，交付物含需求/影响面/验收文档。
- **评审已有规格**：要评审已有规格是否完整、验收标准是否可判定、规格是否过时。

**不用**（直接干，别写规格）：

- 直接实现、有测试覆盖的小改动、纯 CRUD、纯 UI 任务 → 那是 harness-dev / harness-ui-design 的活。
- PR / 代码评审 / 变更验收 → 那是 harness-pr-review 的活，本 skill 不触发。
- 规格已定、进入纯实现阶段 → harness-dev。
- 纯探索/调研（无确定交付物，spec 无锚点）。

## 方法（薄入口：只编排，判据委托核心）

流程：需求 → 规格 → 验收标准 → 评审。

**判定**：按上节 Apply/Skip 触发过一遍；判「用」才往下。

**提案**：写清三件事——要解决什么问题、为什么现在做、边界（明确「不做什么」）。写不出来或互相矛盾 → 需求未清，先澄清再编码。

**规格**：把需求写成可执行规格——功能行为、关键场景、约束（SHALL/MUST），按「最小规格模板」写（见下）。约束语义（建议 vs 约束、落在被消费层）委托 core 二、约束组件，不复制正文。

**验收**：每条验收标准必须可判定（可测/可核对/可验收），写成验收清单，每条绑定验证命令或核对方式。验收标准 = 完成定义，**未全过不标完成**；完成判定口径委托 core 第 4 步「反馈门禁」。

**评审**：独立视角过三关——完整性（覆盖需求？）、正确性（自相矛盾？）、一致性（与现有系统/约定冲突？）。评审边界委托 core 第 4 步独立评审口径（判据以核心为准）。

**落盘**：规格文件进版本控制（建议 `docs/specs/` 按功能命名）= 单一事实源 + 跨会话记忆；实现与验收都从磁盘重读（记忆语义委托 core 记忆组件 + `scripts/record-error.py`）；按 core 编排四纪律② 委托契约五字段对齐（字段清单见核心 SKILL.md），作为交接文档给实现方（harness-dev）；改规格走 PR + 人在环（委托 core 六、受监督自我修改协议）。

### 最小规格模板（`####` 分级的载体）

```markdown
# <功能名> 规格

## 背景与边界
- 要解决的问题：
- 为什么现在做：
- 不做什么（边界）：

## 功能行为
- SHALL：<行为>

## 关键场景
### 场景 1：<名称>
- #### 验收 1.1：<可判定标准>（验证命令/核对方式：<命令或步骤>）
```

### 可执行机制（提炼自 OpenSpec/gsd-core，不依赖其 CLI/生成流水线）

- **spec 先写** — 顺序不可反。后补的规格只是记录，不约束实现。
- **验收标准可判定** — 场景式（SHALL/MUST，`####` 分级，见最小规格模板）；模糊词（差不多/尽快/好用）禁止；空转归档拒绝——「零 delta」= 相对需求范围没有新增约束、没有新增可判定项。
- **范围子集** — 按需求范围选子集：只提案 / 提案+规格 / 全套（含设计任务）。solo 默认「提案+规格」；「全套」仅跨模块且多人时启用。
- **影响面清单** — 跨模块改动列出受影响模块与相互影响（改 A 影响 B/C），逐条核对；不做自动传递闭包（无工具支撑，别写未实现机制）。

### 单人语义（需求方与确认动作）

core 默认单人模式：需求方 = 实现者本人。确认动作降级为「把预期/边界/验收标准写成一条可复核记录」并落盘，不另设审批人。仅当存在真实 reviewer（团队模式）或受监督变更（core 六、）时才要求独立确认。solo 场景拒绝仪式化审批。

## Common Rationalizations

| 借口 | 现实 |
|------|------|
| 小功能不用写规格 | 规模小 ≠ 边界清。需求不清的「小功能」返工成本通常 > 一页规格。 |
| 需求我清楚，直接写代码更快 | 写规格是让验收标准显式化，不是多一道手续。需求方没确认前，代码 = 按你的理解写，跑偏才返工。 |
| 验收标准以后再说 | 没有可判定验收标准 = 没有完成定义，实现无法收敛、评审无锚点。 |
| 先写代码跑通再补规格 | 顺序反了：spec 先写才能约束实现；后补的规格只是记录，不影响已经跑偏的代码。 |
| 规格写完没人看 | 规格是给实现和验收共用的契约 + 跨会话记忆，不是文档任务。 |
| 我们不需要影响面分析 | 跨模块改动不列影响面，改了 A 悄悄破坏 B/C，验收阶段才发现。 |
| solo 项目自己确认自己不算数 | 单人模式确认 = 可复核记录落盘，不是走仪式；没有记录才是自说自话。 |

## Red Flags（自检）

- 规格文件不存在，或只有一句 README 段落。
- 验收标准含模糊词（差不多/尽快/稳定/好用），或没有绑定验证命令/核对方式。
- solo 场景没有把预期/边界/验收标准写成可复核记录并落盘。
- 规格没写「不做什么」（边界缺失）。
- 跨模块改动没有影响面清单。
- 规格含 placeholder（TBD / 待定 / 未决 / XXX）。
- 规格与现有系统/约定冲突未标注。
- 团队/受监督场景没有独立评审记录（solo 可自核，此处不是走过场）。

## Verification（可验证出口）

- [ ] 规格文件存在并落盘进版本控制（核对：`git ls-files docs/specs/` 有对应文件）。
- [ ] 每条验收标准可判定：逐条含验证命令或核对方式（核对：可人工执行）。
- [ ] 无 placeholder（TBD/待定/未决/XXX）。
- [ ] 边界明确：写了「不做什么」。
- [ ] 跨模块改动列出影响面清单（核对：逐条列出受影响模块并注明相互影响）。
- [ ] 确认记录在案：solo = 可复核记录落盘；团队/受监督 = 独立评审记录存指定文件。
- [ ] 规格符合本 skill 最小规格模板（SHALL/MUST + `####` 场景分级）。

## 委托（调用核心哪些部分，不复制）

- **独立评审边界** → core SKILL.md 第 4 步（判据口径以核心为准）。评审是领域步骤，判据口径以核心为准。
- **验收门禁判据** → core 第 4 步「反馈门禁」（判据见核心 SKILL.md 第 4 步）；规格验收清单本身在本 skill 定义（见「验收」），core 不提供规格验收机制。
- **数据正确性抽样** → core 第 4 步（挑 3-5 条真实输出核对，代码对 ≠ 数据对）。
- **返工记忆** → core 第 0.5 步 + `scripts/record-error.py`（规格评审暴露的返工记入 STATE.json）。
- **规格变更** → core 六、受监督自我修改协议（PR + 人在环批准 + 可回滚）。
- **团队场景规格归属** → `references/team-playbook.md`（归属权/变更评审）。
- **激活入口** → 本 skill 落位 `skills/requirements/`（目录短名 `requirements`）。真实启用/禁用走**各运行时原生 skill 启用面**（Claude Code 的 `skillOverrides` / 安装面——本 skill 需进入运行时发现根才可被开关）；`.harness/config.json`（enabled/disabled）与 `HARNESS_SKILLS=dev,requirements` 是**配置声明层**，只被 `skill-router.py` 解析校验与漂移检测，不 gate 运行。defaultMode=all 只表示「在发现面可按 description 触发」，防跨域串味靠 description 触发词 + Skip when + `_meta` 路由引导。
- 不复制 core 的编排/约束/记忆规则；本 skill 只负责需求到验收这一段。
